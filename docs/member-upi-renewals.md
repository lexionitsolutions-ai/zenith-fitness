# Members-only UPI renewals

The checkout displays the ICICI HUF recipient above the payment buttons. App links and the QR are rebuilt from that configuration rather than trusting a stored checkout URI. **Save QR to scan from gallery** downloads the amount-specific QR as a PNG for a UPI scanner on the same phone. Before entering a PIN, confirm the payment app shows `9272112745.etb@icici` and the intended amount.

Members open **Renew membership** on the dashboard (`/renew`). Google Pay, PhonePe, Paytm, a generic UPI chooser, an amount-specific QR and a copyable UPI ID are available. Payments go to **9272112745.etb@icici**, **RAJVARDHAN HEMANT PATIL HUF**, as supplied in the ICICI QR. There are no visitor accounts or online admissions.

The member submits the successful payment's 12-digit bank reference. This creates a submitted approval request, not a confirmed payment. Admin finds the pending count under **Members → UPI renewal approvals** (`/admin/renewals`). The queue refreshes every 30 seconds while visible. Admin must verify the reference and amount against the actual ICICI receipt before approving; rejection requires a reason shown to the member. A static QR cannot provide a verified bank callback. Automatic settlement confirmation would require a bank or payment provider integration. UPI app availability and merchant acceptance depend on the phone, app and bank; the QR and manual UPI ID remain available.

## Prices and dates

The owner-confirmed prices are in `src/constants/membership-packages.ts`. Requests snapshot the server's amount, category, plan name and duration. Female and Female Happy Hours packages require a female member profile. Happy Hours are 10 AM–4 PM during gym opening hours.

An early renewal starts the day after the latest fully paid membership ends, including already approved upcoming periods. An expired membership starts on the approval date in Asia/Kolkata. End date uses start + 30, 90, 180 or 365 days, matching the existing reception convention. The app treats expiry dates as inclusive, so cycles do not overlap. Final dates are calculated under a member lock during approval and shown in renewal history.

Only an active, fully onboarded member can create a request. Account ownership comes from the database, not a submitted member ID. One open checkout per member is enforced by a database partial unique index. UTRs are unique, and submission and approval are locked against duplicate processing. Unpaid drafts can be cancelled; submitted requests require admin review. Approval preserves the member's admission ID and login.

## Sheets delivery

Approval creates the membership and a durable `RenewalSheetsJob` in the same transaction, then attempts delivery. The existing reception deployment receives URL-encoded `saveRenewal` fields: admission ID, member details, duration, category, dates, paid amount, UPI mode and a `ZenithApp:<reference>` marker in remarks. Destination tabs are `Renewals 1M`, `Renewals 3M`, `Renewals 6M`, and `Renewals 1Y`.

The existing server-side reception URL is reused. Optional `GOOGLE_SHEETS_WRITE_URL` overrides it with another deployed Google Apps Script `/exec` URL. It must support `saveRenewal` and the read-only `getMembershipRows` action. No test rows or actual payments are generated by automated checks.

Admin sees delivery separately from approval:

- `FAILED`: read/configuration failure before posting; retry is safe.
- `UNCERTAIN`: interrupted or unconfirmed write. Retry first checks for the reference. Resending requires explicit confirmation that the destination entry is missing.
- `SAVED`: Sheets confirmed the write; retry only reconciles, never reposts.
- `SYNCED`: matching amount, mobile, admission ID and destination row found.
- `PENDING` / `PROCESSING`: awaiting delivery or currently claimed by a worker.

Reconciliation records the real sheet name and row on the membership, so future imports update the same cycle. If an import has already created that exact referenced cycle, reconciliation links the renewal to it and removes the temporary duplicate. Conflicting rows remain visible as sync errors instead of being overwritten. Failed external delivery does not undo an approved membership.

## Deployment

Vercel runs `npm run build:vercel`, applying migrations before building. Other hosts must run `npm run db:deploy` before restarting the new app. The new migration is additive and uses separate `RenewalRequest` / `RenewalSheetsJob` tables, so unused tables from an older UPI deployment are untouched. Do not reset the database.

Rebuild/install the Android APK for app-specific native handoff. Older APKs use a generic external UPI link, with QR/manual fallback. iOS uses generic links with a Google Pay deep link where selected; all apps can scan the QR. A real device and genuine paid transaction are required to verify bank acceptance and final Sheets delivery.

Validation: `npm test`, `npm run typecheck`, `npm run build`. Tests cover ownership, forged input, references, inclusive expiry, atomic approvals, rejection, preserved approvals after delivery failure and safe Sheets retry behavior.

Run `node --env-file=.env --import tsx scripts/check-renewal-integrations.ts` to check the configured database tables and reception export without writing any sheet entries. This uses `.env`; production migration commands must use the production host's `DATABASE_URL`.
